# v3.3.0 Updater Bootstrap Audit

Date: 2026-08-10

Audited historical commit: `2a6ff5ff85d4acad87104c1d67be62a28c317439`
(the v3.1.0 release commit named by the implementation handoff).

## Findings

### 1. Does v3.1.0 check `/releases/latest` automatically?

Yes, for the stable channel. `src/sky_music/ui/textual_app/app.py` schedules
`check_for_updates_worker` three seconds after mount (historical lines
217–225). The worker calls `should_auto_check` and then
`orchestration.update_service.fetch_latest_release`; the stable policy builds
`https://api.github.com/repos/pumni/Sky-Auto-Player/releases/latest`.
The beta policy queries the releases collection and selects the newest valid
non-draft version.

The check is throttled by `update.auto_check` and the persisted check/error
timestamps. It is a metadata check, not an installation trigger.

### 2. Does v3.1.0 notify only or install automatically?

The in-app path is notify-only. The historical update modal offers:

- Download from GitHub;
- Remind me later;
- Skip this version.

The `github` action opens the release page in a browser. There is no call from
the Python UI to download, extract, replace, or restart the application.

The separate legacy path is user-invoked: `updater.bat` starts
`installer/updater.ps1`, which downloads the release ZIP and SHA256 sidecar,
verifies the staged manifest, performs the transactional copy, and optionally
restarts with `-Restart` (historical `installer/updater.ps1` lines 912–1075).

### 3. What assets does v3.1.0 expect?

The historical external updater selects the canonical versioned ZIP and its
matching `.zip.sha256` sidecar. It verifies the embedded `MANIFEST.json` after
extraction. The in-app checker selects a ZIP and optional SHA256 sidecar for
the notification metadata; it does not require a separately downloaded
manifest asset.

The current release contract already publishes the three-asset set:

```text
Sky-Auto-Player-v<version>.zip
Sky-Auto-Player-v<version>.zip.sha256
MANIFEST.json
```

No asset rename is required for the v3.1.0 bootstrap.

### 4. Does v3.1.0 invoke BAT/PowerShell or use an execution-policy bypass?

Only the separately invoked legacy updater does. `updater.bat` calls
`powershell`/`pwsh` with `-NoProfile -ExecutionPolicy Bypass -File` (historical
`updater.bat` lines 17–22). The application’s background update check does not
invoke that script.

This is historical evidence only. The v3.3.0 public package will not ship the
legacy BAT/PowerShell updater.

### 5. What state does the legacy path preserve?

The historical updater preserves `config.json`, `.env`, `songs/**`, and
`logs/**`, and only patches update-notification timestamps in `config.json`
after a successful binary transaction. It stages outside the installation
root, verifies the ZIP sidecar and embedded manifest before mutation, and
retains transaction recovery material on rollback failure.

The native updater must retain these same preservation and rollback
properties.

### 6. Would publishing v3.3.0 automatically trigger legacy installation?

No. A v3.1.0 process may discover the newer tag and show its notification, but
the historical UI does not launch `updater.bat`. Installation requires an
explicit user action outside the app.

### 7. Can v3.1.0 consume the v3.3.0 release triple?

The release-level contract is compatible: the old path recognizes the
versioned canonical ZIP and sidecar, and it validates the embedded manifest.
The external `MANIFEST.json` remains an integrity/provenance asset for the
release and is not required by the old script's download path.

This is a manual bootstrap only. The v3.1.0 legacy updater is not part of the
v3.3.0 public package and is not used by the new Python launcher. A clean
manual extraction into a new directory is the supported migration path if an
old install cannot safely run the legacy updater.

## Decision

Proceed without changing canonical asset names. Users migrate manually from
the public v3.1.0 release to v3.3.0. Once running v3.3.0, the user-triggered
native `Update and Restart` path owns subsequent updates.

This audit does not claim an RC-to-RC or packaged cross-version acceptance
result; those require exact Windows artifacts and manual execution.
